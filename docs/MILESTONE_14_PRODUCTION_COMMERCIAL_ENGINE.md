# Milestone 14 — Regstead Production & Commercial Engine

Status: COMPLETE — locally validated standard-subscription beta implementation; staging/provider launch steps remain explicit. M13 release: `1f45cc3f648bbd8d70e538f25ef29ba397e35dcf`.

> Commercial model updated by M14.1: Regstead Scan £0; Regstead Monitor £16.99/month for one primary website. See [M14.1](MILESTONE_14_1_COMMERCIAL_SIMPLIFICATION.md). Original M14 validation numbers below are historical.

## Architecture checkpoint (before implementation)

The existing crawler, snapshots, PDF/browser extraction, comparison, generic rules and LawWatch modules remain WatchLayer engine code. No limits or evidence policies change. A new `src/regstead/` layer owns organisations, subscriptions, scheduling, jobs, human review and report delivery. It calls `scanLawWatch` through an injected engine adapter and records exact versions and an immutable engine reference.

Commercial persistence has a transaction-based repository interface. SQLite provides a durable single-host standard-subscription beta implementation in a separate database; the engine keeps its existing database naming. A PostgreSQL adapter uses the same transactional model with an explicit row lock. Short serialized operational transactions protect claims, subscription updates, release and outbox creation. No network work occurs under a database transaction. Versioned migrations are separate from engine migrations. The initial small-cohort implementation favours correctness over high-throughput queue infrastructure; no Redis is required.

Workers claim leased jobs with fencing tokens, renew leases and checkpoint scan completion before draft publication. A job-specific engine database permits recovery of a completed engine run after a process crash without rerunning it. Database scheduling uses explicit cadence and bounded catch-up, entitlement checks and per-site overlap prevention. Human decisions are append-only overlays; release freezes a stable HTML artifact with a content hash. Storage is an immutable put/get interface with a filesystem adapter.

The operator boundary is an authenticated CLI. A small HTTP service accepts verified raw-body Stripe webhooks and exposes health/readiness only. Billing uses a Stripe provider interface and the official SDK; local test fixtures make no provider calls. Server-owned checkout records bind terms, organisation, Regstead price and subscription metadata. Webhooks reconcile current provider subscription truth, with event deduplication and serial processing to avoid out-of-order resurrection. One configured Monitor price is used; cancellation permits later resubscription at the currently configured price. The shared Foundry Vale Stripe account is isolated by product, prices and metadata.

Notifications use a transactional outbox and a provider-neutral idempotent send interface. Report notifications require a released reviewed report. The default delivery adapter is a local file spool; a real provider must honour durable idempotency keys before production sending is enabled. No live email, payment, cloud resource or deployment is performed by this milestone.

## Implementation and operating model

All new commercial code is under `src/regstead/`: `types`, `repository`, `operations`, `worker`, `engine`, `reports`, `billing`, `notifications`, `config`, `http` and `cli`. Existing engine implementation files are unchanged from M13. The package remains WatchLayer. Dependencies added are the official Stripe SDK 22.6.0, PostgreSQL driver `pg` and its development type declarations. Stripe requests pin API version `2026-08-26.dahlia`.

### Data model and migration

Organisation records retain legal/display names, contact information, lead/active/inactive status, timestamps. Each organisation has one primary monitored site with normalized URL/hostname, LawWatch pack, browser opt-in, pause/active state, cadence, next due time and last successful run. Onboarding creates the organisation, primary site and free baseline together. Duplicate primary hostnames are rejected; operators must confirm legal organisation identity before onboarding a second domain.

Subscriptions retain provider/customer/subscription/price identifiers, current status, period end, cancellation-at-period-end and explicit grace deadline. Checkouts retain locally accepted terms version/date, server-selected price and Stripe session/subscription linkage. Jobs retain exact engine, LawWatch, browser and deployed Git versions. Runs retain the immutable engine reference, scan/profile/baseline and metrics. Reports, review overlays, webhook receipts, notification delivery and structured audit events are separate typed collections.

Commercial migration 1, revised pre-launch by M14.1 with the `monitor-v1` model marker, creates a versioned transactional aggregate in `regstead_state`, separate from all WatchLayer engine migrations. SQLite uses WAL, full database transactions and a busy timeout; PostgreSQL uses a row lock and parameterized writes. Older M14 development databases are rejected without conversion; configure a fresh commercial database and retain old fixtures separately. Migration startup is serialized (SQLite transaction / PostgreSQL advisory transaction lock), repeatable and rejects unsupported versions. `DOWN_1` exists for an empty/disposable database; it is destructive and must never be used on customer history without a separately approved export/retention procedure.

This deliberately serialized aggregate is suitable for a small, single-host initial pilot, not a high-throughput multi-tenant platform. Each transaction reads/writes operational metadata, including review results; full engine archives remain outside it. History growth increases transaction cost. Monitor database size/latency and migrate to normalized, indexed per-entity tables before expanding volume. PostgreSQL removes dependence on SQLite for commercial state, but engine databases and report artifacts still need durable storage shared with the worker. The PostgreSQL adapter transaction contract is tested; an actual PostgreSQL instance was unavailable in this environment. No claim of deployment-tested PostgreSQL throughput is made.

### Jobs, recovery and scheduling

Job types are BASELINE, MONITORING and MANUAL_RECHECK. States are QUEUED → RUNNING → AWAITING_REVIEW → APPROVED → RELEASED, with FAILED/CANCELLED alternatives. Workers acquire a 120-second lease with a unique fencing token, renewed every 20 seconds. Database transactions reject stale completion. Recovering an expired lease and transient retries are bounded to two automatic retries. Retries retain job identity. Permanent failures require an operator decision. Retry backoff is 60 then 120 seconds. The least recently served organisation is preferred; only one running job per organisation is allowed. Worker concurrency is configurable from one to four; the default is one.

Each job has its own WatchLayer database named `watchlayer.db` inside its job directory. A monitoring job starts with the last commercial run's engine history, so the existing comparison eligibility rules still apply. A manifest records the comparison input. A completed engine result is recoverable if the process exits before the commercial checkpoint; a persisted commercial run is reused if it exits before draft publication. A process lock prevents concurrent writes to the job's engine database. On a single host, an orphan lock is removed only after confirming its PID is no longer alive; a lock belonging to another host requires operator investigation. Live PID reuse errs towards blocking rather than unsafe removal.

Production workers reject jobs pinned to a different deployed release. Drain jobs before upgrading; inspect/requeue explicitly under the new release if necessary. Do not simply relabel historical engine results. SIGTERM/SIGINT stops new work and waits for bounded active work. A force kill is recoverable through leases and checkpoints. Configure the supervisor's termination grace to suit the maximum bounded crawl duration.

Monitoring uses configured milliseconds, one due job per site, no overlap through review, and at most one catch-up scan after downtime. The next due time advances from the scheduling time. Inactive, paused, expired and unentitled sites are skipped. Queued monitoring is rechecked at claim time. Explicit operator rechecks and the requested free baseline are separately authorized and may run without paid entitlement. Delayed human review intentionally delays subsequent scans.

### Review and report lifecycle

Every engine result becomes a draft finding. Its raw state, explanation and structured evidence remain unchanged. Review decisions append APPROVED, SUPPRESSED or ANNOTATED overlays with named reviewer, timestamp and note. Annotations can change customer title/explanation, never the raw engine state. All findings must have a decision before release. Broad legal-conclusion phrases are rejected in operator annotations. This guard complements, rather than replaces, human review.

Release produces a stable self-contained HTML artifact. Its metadata includes report/version, organisation/site, timestamps, exact engine/rule/browser/build versions, reviewed findings, citations, changes and limitations. Vocabulary is Confirmed, Review recommended, Action recommended, Could not confirm and Not applicable. UNKNOWN is never converted into absence. The Regstead / Foundry Vale disclaimer expressly disclaims certification. HTML is escaped and carries a restrictive CSP. There are no scripts, remote assets or customer authentication pages.

Artifacts are content-addressed and immutable. Publication uses an exclusive filesystem link after writing the temporary artifact. Releasing again returns the same report. If a review changes during storage, release is refused; the unused artifact may remain for operator reconciliation. The final database transaction freezes the report and queues notifications atomically. Original reports are never regenerated after an engine update. `export` writes a new local copy without overwriting an existing file. Private customer delivery is operator-assisted in this milestone; the HTTP service does not expose report URLs.

### Billing, terms and the standard subscription

Checkout uses Stripe-hosted subscription Checkout, not card collection or coupons. Server configuration selects one monthly GBP Price of 1699 pence under the Regstead product. This is the amount before separately configured Stripe tax behaviour; VAT inclusion/exclusion must not be inferred. The official SDK retrieves and verifies catalog ownership, amount, interval and currency before creating Checkout. A stable local checkout ID is the Stripe idempotency key and server-side ownership link. Subscription metadata identifies Regstead and the originating organisation/checkout. The shared Foundry Vale account's unrelated products/prices are ignored.

The operator records the customer's acceptance of the current terms version; the CLI is not authority to accept terms on the customer's behalf. Acceptance timestamp and version are retained locally. The Stripe Billing Portal service opens the linked customer's Stripe-hosted portal. Dedicated Regstead customers are created by this Checkout flow; do not manually substitute customers shared with another Foundry Vale product. Configure the Stripe Billing Portal to expose only the intended Regstead actions/prices before launch.

There is no allocation, reservation, capacity gate, retained-price promise or forfeiture state. Final cancellation stops monitoring and retains historical reports. The customer may later subscribe at the configured Monitor price.

Supported events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`. Raw body signatures, timestamp tolerance and configured live/test mode are verified before storing the minimal event record. Raw webhook bodies and payment details are not persisted. HTTP acknowledges durable receipt; workers process separately. Event IDs deduplicate side effects. Processing is serialized with a lease, retrieves current Stripe subscription truth, validates Regstead product/price/metadata and binds it to the server checkout. An old invoice payload cannot revive a cancelled subscription. Failed events are visible and manually retryable. Failed or unknown invoice events never grant entitlement based only on their names.

Payment failure uses an explicitly configured grace period (default zero). Repeated failure events do not extend it. A subscription scheduled to cancel remains entitled only through its paid period; final deletion stops future monitoring. History is retained. Refund/dispute operations remain an operator duty in Stripe during the initial pilot; those additional event families are not automatically adjudicated by M14.

Stripe references: [webhook signatures and delivery](https://docs.stripe.com/webhooks), [subscription lifecycle](https://docs.stripe.com/billing/subscriptions/webhooks), [Checkout creation](https://docs.stripe.com/api/checkout/sessions/create), [portal creation](https://docs.stripe.com/api/customer_portal/sessions/create). No live Stripe API calls, products, prices, charges or cloud resources were created during implementation.

### Notifications and customer delivery

The transactional outbox supports onboarding, baseline-ready, monitoring-ready, reviewed material-item, payment-failure and cancellation templates. Report/material notices require a released report and cannot bypass review. Delivery records retain queued/sending/sent/failed state, attempt count/time, provider reference and a fencing token. Retries reuse a stable notification ID as the provider idempotency key.

The supplied adapter is a durable local spool: SENT means accepted into that adapter, **not delivered to a real inbox**. This is explicit in the runbook and configuration. A real email provider adapter must guarantee durable idempotency or reconcile ambiguous sends before retrying; database transactions alone cannot promise exactly-once external delivery. Private report export/delivery and installing/configuring that provider are manual launch steps. No real emails were sent. The application rejects unsupported EMAIL_PROVIDER values rather than silently selecting a different delivery method.

### Security, observability and retention

The CLI authenticates against environment-injected operator credentials and requires a reviewer/operator identity. It is an internal host tool, not a public customer API. OS permissions remain part of its security boundary. The HTTP service exposes only health, readiness and the verified Stripe webhook; it has no unauthenticated admin routes. Put it behind HTTPS with ingress/body/rate limits in production. SQL is parameterized, commands do not invoke a shell, onboarding reuses WatchLayer public-address validation, and the engine rechecks network boundaries during crawling. Browser limits and policies are unchanged.

Audit events use IDs and operational codes; notes, unrestricted evidence and provider secrets are excluded from structured operational logs. Job queue/start/scan success/failure, browser attempts, awaiting-review, release, webhook receive/process/failure and email queue/send/failure are recorded. Engine-derived inability to observe a page remains report uncertainty, not an operational job failure. Typed operational failures include NETWORK_TRANSIENT, ROBOTS_BLOCKED, BROWSER_POLICY_BLOCKED, ENGINE_FAILURE, REPORT_GENERATION_FAILURE, STORAGE_FAILURE, EMAIL_FAILURE, STRIPE_WEBHOOK_FAILURE and INVALID_CONFIGURATION. ROBOTS/BROWSER codes are available at the boundary; ordinary bounded browser failures stay in engine metrics rather than failing an otherwise useful scan.

Readiness checks database access, recent worker heartbeat, engine version/runtime and billing configuration presence. It does not establish external provider reachability, an installed/runnable Chromium binary, deliverability, or full deployment correctness; those are launch smoke checks. A stale worker heartbeat makes readiness fail. Configuration errors fail startup; error output does not dump environment variables. Live/test mode and a deployed release SHA are explicit. Store restricted Stripe credentials in a secret manager, injected at runtime; use separate isolated sandbox credentials for staging.

Normal cancellation changes status and entitlement, not historical records. There is deliberately no destructive delete command. The deletion/anonymisation pathway is a separately approved operator procedure: identify all organisation/site/job/report references, export required audit/billing records according to the final policy, redact contact fields and free-text notes, remove artifacts/engine copies as authorized, reconcile provider records and verify backups expire according to that same policy. Legal retention periods are not invented in code. Until a policy is approved, no automatic purge is enabled. Restrict database/spool/artifact access, encrypt production disks/backups and test restoration.

### Deployment and limitations

Node >=22.16 is required by the engine; the container uses Node 24. It installs the lockfile-pinned Playwright Chromium and Linux dependencies, runs unprivileged and stores data under a mounted volume. Build with `docker build`; run separate worker and webhook service processes against the same commercial database and durable paths. SQLite is single-host only; do not place it on a network filesystem. PostgreSQL commercial persistence may be used with the tested repository contract, but its real-server integration and volume topology require staging validation. Worker engine artifacts must not be concurrently edited across hosts. For this pilot, prefer one worker host and concurrency one.

No Docker executable or PostgreSQL server was available here; image build and real PostgreSQL integration were not run. The Dockerfile is provider-neutral packaging, not a deployed service. Base images should be pinned to an approved digest by the deployment pipeline. The lockfile pins application dependencies and the image installs the matching Chromium version. No WordPress/Gravity Forms changes, polished dashboard, live deployment or M15 work were performed.

M13's live-render limitations carry forward: seven E&W rendering gaps triggered, zero recoveries, four robots blocks and three network-policy blocks. Browser fallback remains selective and best-effort. Nothing in commercial activation, billing or report wording turns those failures into absence or proves live precision.

## Validation coverage and corrections

The new local tests exercise the complete simulated standard-subscription beta lifecycle: organisation/site → Checkout fixture → verified-event boundary → baseline worker → persisted engine result → draft → mandatory per-finding review → immutable release → outbox → scheduled monitoring → renewal → payment failure/grace → cancellation → retained historical report. Separate integration fixtures call the actual unchanged WatchLayer scanner with deterministic HTTP responses and the actual authenticated CLI for inspection, review, release and export.

Regression cases cover concurrent queue claims, stale fencing, crash recovery before the commercial checkpoint and before draft publication, transient retry limits, permanent failure, organisation fairness, pause/entitlement checks, bounded scheduling catch-up, duplicate checkout/invoice events, out-of-order cancellation protection, cross-product/price/organisation isolation, terms acceptance, signature tampering/timestamp/mode, unsafe URLs, operator authentication, transaction rollback, immutable storage, concurrent review/release, storage errors, notification gating, ambiguous send acknowledgement, exact versions, release mismatch, HTML escaping, conservative wording, PDF page/rendered provenance, and corrupted artifact export.

Integration review corrected two new-layer problems before release: change/drift results were already included in the LawWatch results array and must not be appended again; a paused automatic monitoring job must also be checked at claim time. The tests protect both. Report citations retain bounded quoted snippets and PDF page/rendered source labels, and report artifacts retain reviewer identity/time. No WatchLayer detector, classifier, browser limit, robots or network policy was changed.

## Remaining launch steps and recommendation

M14 provides an operator-led standard-subscription beta engine, not a deployed SaaS service. Before taking payment, run the staging/container and actual selected-database checks, configure isolated Stripe sandbox/live resources and portal policies manually, approve customer terms/retention/VAT handling, verify backups/restore and restricted secrets, and either install an idempotent real email provider or explicitly operate secure manual report delivery. Monitor unreleased review queues and subscription events. Engine-history copies and the serialized commercial aggregate need storage/latency monitoring as history grows.

M15 is planned to add the Regstead Customer Portal for report access. It is distinct from the Stripe Billing Portal and has not been started. Staging, real provider and operational validation remain necessary before a live customer pilot.
